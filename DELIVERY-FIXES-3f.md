The 20 breakages: the engines awaited with `Promise.all` again (the review race); a closed attempt still letting a sibling start a request; a request counted on an attempt no longer open; "no call" allowed after a request started; a failed recording's requests not recorded; ownership not checked when a queued leg's turn comes (**survived alone**); the completion write not guarded by the owner; provider requests not gated on ownership; no heartbeat; a takeover not becoming the owner; the export adding older checks to request totals; older checks without their own subtotals; a pre-3e attempt's unknown start count read as 0; 3d parser attempts keeping the bound of 1; the original bound not preserved; the migration not run once only; 3d attempts mistaken for request-counting ones; new recording attempts not marked as counting requests; and two combinations: the turn check removed together with the request gate, and together with the guarded save.

**The survivor, explained:** the ownership check when a queued leg's turn comes is a first line of defence. If it is removed, a tap that no longer owns the leg still sends nothing (the request gate refuses its first request) and saves nothing (the completion write is guarded by owner), so nothing observable changes. Removing it **together with** either backstop is caught (both combinations above), so each layer is needed.

**Found by the breakage run and fixed in the test (not the app):**
- "New recording attempts not marked as counting requests" first survived: no test interrupted a NEW recording. Added: an interrupted new recording (2 requests made, its spend never written, then forgotten) is reported as "(2 had been started), at most 3", never as an attempt from before Fixes-3e. Caught.
- Three breakages (the request gate, a takeover not becoming the owner, and the turn-check-plus-gate combination) were first caught only because an extra request waited forever in the test's hold queue. The test now lets any extra request go straight out once the expected ones are released, so each is caught by its own named check (for example "4 parser checks ran", "the second tap took over only the abandoned queued work"). F6, F7 and F9 were rerun on this final test with the same results.

**Unpopulated export example:** `FitLife-Voice-Calibration-EXAMPLE-unpopulated-3f.xlsx`, from the real export route on a brand-new database: 17 sheets; the ledger line shows 0 and 0, no UNRESOLVED, no older checks.

**What remains true, stated plainly:**
- If a server stops during a request, whether it was answered or charged cannot be known. The kit records how many had started (from Fixes-3e on), the most there could be, and leaves the rest to an administrator reading the provider's usage records.
- For attempts from before Fixes-3e, how many requests started was never recorded; the kit says so instead of showing 0. Their parser bound of 12 is the most the code of that time could make in any configuration, not a guess at what it did.
- The heartbeat keeps a running check owned while its tap is alive. If a tap's process stops, its claim can be taken over 10 minutes after its last renewal: that is the abandoned-work recovery, and a tap that later comes back can neither run nor save that leg.
- Settlement is still an admin route, not a panel button.
