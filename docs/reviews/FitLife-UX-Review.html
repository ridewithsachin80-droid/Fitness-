FitLife / Product, UX & implementation review / 12 October 2026

Make logging feel like a small part of the day.

FitLife already has substantial functionality. Its strongest opportunity is to make that functionality easier to reach, easier to trust, and faster to repeat. The new interface puts the day and three logging actions first.

Based on the supplied GitHub test branch, source and workflow inspection, local regression checks, browser previews, and official competitor documentation. This is an implementation and product review, not a live production audit or a member usability study.

What is built

Implemented in the supplied update

  • A calm dark and light Home. One nutrition summary, protein/carbs/fat, water, movement, sleep and weight. A restrained jade palette, consistent spacing and fewer competing panels.
  • One primary logging dock: Speak / Snap / Type. Speak requests recording from the original tap; Type focuses the input; Snap invokes the rear-camera capture input. Photo-library selection remains a separate attachment action.
  • A quieter AI workspace. Less repeated heading text, a compact attachment menu, readable review cards, editable grams and macros, and one explicit save action. Photo selection automatically requests analysis; saving still follows member review.
  • Three main destinations: Today, Progress, More. The complete plan is directly accessible from Home. More provides labelled links to existing food, checklist, nutrition, coach, health, device and settings tools.
  • Progressive disclosure. Plan & tools, daily entries, and Insights & coach start collapsed. More opens the relevant section or sheet directly.
  • Better correctness. Past-day autosave and date-change protection, explicit save retry, date-correct weight comparison, real movement values instead of illustrative steps, and examples that populate a draft without submitting it.
  • Safer private caching. Authenticated API cache keys are partitioned by a hash of the session token. Authentication responses are excluded; private and legacy API caches are cleared on sign-out.
  • Less loading work on entry. Plan, Progress, Profile, Settings, devices and staff routes are loaded as separate chunks. The main JavaScript bundle is approximately 697 KB versus 1,152 KB previously, before compression. This is a build-size comparison, not a measured improvement in real-device load time.

Camera qualification: the implemented capture input asks a supported mobile browser for the rear camera. Desktop browsers generally use a chooser, and mobile OS/browser behavior varies. Direct camera behavior on the intended Android/iPhone/PWA installations remains a release check. This build does not claim universal camera-only behavior.

Comparison with leading apps

These are documented product patterns, not an independent ranking or a hands-on timing benchmark. Features can vary by subscription, platform and region. References were checked on 12 October 2026.

AppVerified patternWhat FitLife should learn
MyFitnessPal [1]Voice food logging with serving and meal review before logging. Its documentation lists limits including water, weight and exercise in that voice workflow.Make FitLife’s mixed daily message flow easy to understand and correct. Broader parsing is useful only when the member trusts what will be saved.
Cronometer [2] [3]Photo matching followed by serving/match edits and diary confirmation. Repeat items can prompt scheduled logging.Prioritize provenance and correction. Reuse FitLife’s existing meal presets to remove repeat effort; avoid silently adding foods the member may not have eaten.
MacroFactor [4]Unified food logging methods, history and favorite foods, configurable shortcuts, natural-language Describe, and a reviewable plate.Keep input methods connected. Surface members’ own frequent foods and portions before asking for a new search or another AI estimate.
Healthify [5]The US product page advertises photo Snap, AI search, Ria chat and human coaching. Voice calls were labelled “Coming Soon” on the retrieved page.Connect logging to helpful coaching. A member should see how an entry helps their plan, with a clear route to a human when needed.
Fitbod [6]Workout recommendations use preferences, equipment, training history and recovery; recorded performance informs later suggestions.Surface FitLife’s existing training history and suggested loads at the moment of logging. Retain coach ownership of prescribed plans.

Product judgement: AI photo and voice alone are not enough to make FitLife distinctive. Its opportunity is one connected daily log, familiar local foods and portions, correction memory, and a coach who sees the same record. That is an inference from the comparison and the existing code, not a claim of measured competitive superiority.

Findings fixed during this review

FindingChange and evidence
Past-day edits could miss autosaveRemoved today-only saving; debounced saves now cover the selected date. A failed save prevents date-arrow navigation and exposes retry. Regression covers a historical weight edit and failed-save recovery.
Weight comparison used today’s yesterdayFetches the day before the selected entry, resets stale comparison state and ignores late responses after a date change.
API caches used URL-only keysSession-scoped cache keys, auth exclusion and logout cleanup. Eleven helper checks cover session separation, token rotation, unchanged network URL and deletion behavior. This is not a penetration test.
Example chips submitted example textThey now fill a focused, editable draft. A regression verifies that no request is sent merely by selecting an example.
General food names overrode specific defaultssmartGrams('egg white') returned 55 g instead of its configured 30 g; chicken curry returned 150 g instead of 200 g. Specific names now match first. Six checks cover this behavior. Defaults remain estimates.
Celebration could interrupt a formMilestone display is deferred while a sheet or AI composer is open.
Large eager route bundleSplit major member and staff routes. Main entry shrank by about 39% uncompressed and 35% gzipped in local builds. Total application code and PWA precache remain larger than this entry.

Reuse existing presets, recent meals and personal labels. Offer one relevant repeat suggestion inside the assistant, not another permanent Home card. Validation and release limits

Production build: passed.
  • 56 premium member-flow/navigation assertions passed.
  • 56 premium browser assertions passed across 320, 390 and 1280 px, light/dark, including enlarged-text AI checks.
  • 14 logic/source-contract suites: 815 checks passed. Private-cache checks: 11 passed. Specific-portion defaults: 6 passed.
  • The broader combined UI run recorded 594 passing assertions before stopping. The remaining macro/overflow/security-policy group passed 207 checks; the device/recovery/honest-state group passed 50 checks in a focused rerun. Counts overlap; this is not a claim that one uninterrupted full suite completed.
  • Actual Home, AI review and More captures were inspected. More also rendered without horizontal overflow at 390 px in both themes.

Detailed scope and limitations are recorded in VALIDATION.json. Existing test fixtures use simulated API responses.

Local checks exercise actual components with fixture APIs. They do not establish live AI nutrition accuracy, real database migrations, production uptime, or successful third-party integrations. PostgreSQL is unavailable in this environment; the database integration suites and workout-merge DB check remain unverified. No real-member logs, live AI provider calls, payments or external notifications were used for these checks.

API-cache helper checks do not replace testing an installed service worker through a real account switch. Auth token rotation starts a fresh cache partition. Cache retention limits and a full storage/security review remain follow-up work.

Small pilot: ask 8–12 representative members, including someone using larger text and someone who speaks mixed languages, to log a meal photo, a mixed voice update, a repeat breakfast, a past-day correction and an interrupted save. Record taps, time, uncertainty and errors. Compare against the previous build; do not infer retention gains from visual polish alone.
